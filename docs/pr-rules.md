# プルリクエストルール（saigai_map）

5人チーム・短期開発（〜8/22-23本番）向けの最低限のルール。厳密さより「事故らないこと」「レビューが滞らないこと」を優先する。

## ブランチ運用

- `main` への直接pushは禁止。必ずブランチを切ってPR経由でマージする
- ブランチ命名: `種別/内容`（英語・kebab-case）

| 種別 | 用途 | 例 |
|---|---|---|
| `feature/` | 新機能 | `feature/route-search-api` |
| `fix/` | 不具合修正 | `fix/hazard-overlay-opacity` |
| `setup/` | 環境構築・初期設定 | `setup/init-project` |
| `docs/` | ドキュメントのみ | `docs/update-claude-md` |
| `refactor/` | 挙動を変えない改善 | `refactor/db-session` |

## コミットメッセージ

`種別: 内容` の形式（[Conventional Commits](https://www.conventionalcommits.org/)の簡易版）。

```
feat: 経路検索APIのエンドポイントを追加
fix: 浸水深オーバーレイの不透明度が反映されない不具合を修正
docs: CLAUDE.mdにGit運用ルールを追記
```

日本語・英語どちらでも良いが、1つのPR内では統一する。

## PRを作るタイミング

- **1機能 = 1PR** を基本にする。差分が大きくなりすぎたら分割を検討する（目安: 変更行数300行超えたら一度立ち止まる）
- 作業に時間がかかる場合は、完成を待たず **Draft PR** で早めに共有する（方向性のズレを早期発見するため）

## PRの書き方

タイトル: `[種別] 概要`（例: `[feat] ハザード考慮ルートの計算エンジン実装`）

本文には最低限これを書く。

```markdown
## 変更内容
（何をしたか、なぜそうしたか）

## 確認方法
（レビュワーが実際に動作確認する手順）

## スクリーンショット
（UIに変更がある場合のみ）

## チェックリスト
- [ ] ローカルで動作確認済み
- [ ] .env や秘匿情報がコミットに含まれていない
- [ ] 関連するドキュメント（CLAUDE.md等）を更新した（必要な場合）
```

## レビュー（可能であれば）

- **可能であれば1人以上の承認（Approve）を推奨**。マージはApprove後、PR作成者以外が行う
- レビューは可能な範囲で当日中に対応する（ハッカソン期間中はこれより早いサイクルが必要になる想定）

## マージ方法

- **Squash and merge** を基本とする（1PR = 1コミットとしてmainの履歴を綺麗に保つ）
- マージ後はブランチを削除する

## コンフリクト対応

- レビュー依頼前に、コンフリクトが起きていないか（`main`を取り込んで最新化したか）を確認する
- コンフリクトが発生したら、**そのPRの作成者が解消する**のが基本

## Claude Codeを使う場合

- Claude Codeはブランチ作成〜PR作成までを担当し、**マージは人間が行う**
- Claude Codeが作成したPRも、上記と同じレビューフローに従う（人間のPRと特別扱いしない）
